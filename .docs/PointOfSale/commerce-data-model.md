# Commerce Data Model and Migration Draft

**Status:** Review draft. This is a schema contract, not an implemented
migration set.

## 1. Design Summary

The first release uses ten domain tables:

1. `product_categories`
2. `products`
3. `stocks`
4. `customers`
5. `registers`
6. `till_sessions`
7. `orders`
8. `order_items`
9. `payments`
10. `stock_movements`

Existing framework tables remain unchanged. Product images use the existing
Spatie Media Library `media` table and a `product_gallery` collection.

The schema intentionally has no variations, suppliers, purchase orders,
warehouses, coupons, reviews, wishlists, or carts. Livewire carts are transient;
held POS carts use `orders.status=held`.

## 2. Enum Contracts

Enums are PHP backed enums stored as documented strings, following current
Aureon conventions.

| Enum | Values |
| --- | --- |
| `ProductStatus` | `draft`, `published`, `archived` |
| `OrderChannel` | `web`, `pos` |
| `OrderStatus` | `held`, `pending`, `confirmed`, `processing`, `ready`, `completed`, `cancelled` |
| `OrderPaymentStatus` | `unpaid`, `partial`, `paid`, `refunded` |
| `FulfillmentType` | `counter`, `pickup`, `delivery` |
| `PaymentMethod` | `cash`, `mobile_money`, `card`, `bank_transfer`, `cash_on_delivery` |
| `PaymentStatus` | `pending`, `completed`, `failed`, `voided`, `refunded` |
| `StockMovementType` | `opening`, `adjustment_in`, `adjustment_out`, `order_commit`, `order_cancel` |
| `TillSessionStatus` | `open`, `closed` |

Status transitions are enforced by services. Database strings make later enum
additions additive and avoid vendor-specific database enum migrations.

## 3. Money and Quantity Contract

- Money columns end in `_minor` and store integer minor units.
- Currency is copied to each order as an ISO 4217 three-character code.
- A small `Money` value object and Eloquent cast may format and combine values,
  but the database remains ordinary integers.
- Tax rates are basis points. `1600` means 16 percent.
- Quantities are positive integers in version one.
- Negative stock is rejected unless a future configuration explicitly enables
  overselling.

## 4. Table Contracts

Every migration column must include a concise `->comment()` describing its
purpose and units. Foreign-key delete behavior is explicit below.

Externally addressable resources receive a separate `char(26)` ULID with a
unique constraint. Integer `id` columns remain primary keys and all foreign
keys remain integers. ULIDs are generated by the module's immutable `HasUlid`
concern and are not mass assignable.

### 4.1 `product_categories`

Purpose: hierarchical storefront and administration navigation.

| Column | Type and constraints | Notes |
| --- | --- | --- |
| `id` | primary key | Category identity |
| `ulid` | char(26), unique | Administrative route identity |
| `parent_id` | nullable FK to self, null on delete | Optional parent category |
| `name` | string(120) | Display name |
| `slug` | string(160), unique | Public route key |
| `description` | text, nullable | Optional category copy |
| `sort_order` | unsigned integer, default 0 | Manual ordering |
| `is_active` | boolean, default true | Storefront visibility gate |
| timestamps | timestamps | Audit timing |

Indexes: unique `ulid` and `slug`; composite `parent_id, is_active, sort_order`.

Model responsibilities:

- `parent()` and `children()` relationships;
- `products()` relationship;
- active and ordered scopes;
- no recursive delete cascade.

### 4.2 `products`

Purpose: simple-product catalog, pricing, publication, and commerce identity.

| Column | Type and constraints | Notes |
| --- | --- | --- |
| `id` | primary key | Product identity |
| `ulid` | char(26), unique | Administrative/API route identity |
| `category_id` | nullable FK, null on delete | Primary category |
| `created_by` | nullable FK users, null on delete | Original administrator |
| `updated_by` | nullable FK users, null on delete | Last administrator |
| `name` | string(180) | Product name |
| `slug` | string(200), unique | Public product route key |
| `sku` | string(80), unique | Internal/scanner product code |
| `barcode` | string(80), nullable, unique | Optional keyboard-wedge barcode |
| `status` | string(30), default `draft` | `ProductStatus` value |
| `short_description` | text, nullable | Product-card/detail summary |
| `description` | long text, nullable | Full product detail content |
| `price_minor` | unsigned big integer | Regular selling price |
| `sale_price_minor` | nullable unsigned big integer | Promotional selling price |
| `sale_starts_at` | nullable timestamp | Optional sale-window start |
| `sale_ends_at` | nullable timestamp | Optional sale-window end |
| `cost_price_minor` | nullable unsigned big integer | Internal unit cost, never public |
| `tax_rate_bps` | unsigned small integer, default 0 | Product tax snapshot source |
| `is_tax_inclusive` | boolean, default true | Whether catalog price includes tax |
| `track_stock` | boolean, default true | Whether availability is enforced |
| `is_featured` | boolean, default false | Basic storefront merchandising |
| `published_at` | nullable timestamp | Publication timing |
| timestamps | timestamps | Audit timing |
| `deleted_at` | nullable timestamp | Soft archive safety |

Validation invariants:

- `price_minor >= 0`;
- sale price is null or non-negative and normally lower than regular price;
- sale end follows sale start;
- `tax_rate_bps <= 10000`;
- published products require a name, SKU, non-negative price, and at least one
  product image only if product policy later makes media mandatory.

Indexes:

- unique `ulid`, `slug`, `sku`, and nullable `barcode`;
- composite `status, published_at`;
- composite `category_id, status`;
- composite `is_featured, status`;
- searchable `name` index where supported; use ordinary LIKE search initially.

Model responsibilities:

- implements `HasMedia` with `product_gallery`;
- `category()`, `stock()`, `orderItems()`, and `stockMovements()`;
- `effective_price` attribute applies an active sale window;
- `is_on_sale`, `is_in_stock`, and `available_quantity` attributes;
- `published()` and catalog-filter scopes.

### 4.3 `stocks`

Purpose: one fast stock projection per product.

| Column | Type and constraints | Notes |
| --- | --- | --- |
| `id` | primary key | Stock row identity |
| `product_id` | FK products, unique, cascade delete | One balance per product |
| `on_hand` | signed big integer, default 0 | Current sellable units |
| `low_stock_threshold` | unsigned big integer, default 0 | Dashboard warning threshold |
| `updated_by` | nullable FK users, null on delete | Last manual actor where relevant |
| timestamps | timestamps | Projection timing |

`on_hand` is signed to permit compensating arithmetic, but service rules reject
a negative final balance. Direct model updates are prohibited by convention;
`InventoryService` is the write boundary.

## 5. Ordered Migration Plan

Timestamps are placeholders; implementation will assign a single ordered
sequence.

| Order | Migration | Depends on |
| --- | --- | --- |
| 1 | `create_product_categories_table` | none |
| 2 | `create_products_table` | categories, users |
| 3 | `create_stocks_table` | products, users |
| 4 | `create_customers_table` | users |
| 5 | `create_registers_table` | none |
| 6 | `create_till_sessions_table` | registers, users |
| 7 | `create_orders_table` | customers, users, registers, till sessions |
| 8 | `create_order_items_table` | orders, products |
| 9 | `create_payments_table` | orders, till sessions, users |
| 10 | `create_stock_movements_table` | products, users |

Migration rules:

- every column uses `->comment()`;
- ULID-bearing tables create `ulid` immediately after `id` with one unique
  constraint; no redundant standalone index is added;
- every foreign key specifies delete behavior;
- strings naming enums mention the PHP enum in their comments;
- money comments explicitly say `minor units`;
- tables use InnoDB-compatible constraints for Hostinger/MySQL deployment;
- SQLite-compatible migrations remain required for the automated suite;
- no destructive changes to existing user, media, activity, institution, mail,
  or report tables;
- rollback order is the reverse dependency order.

## 7. Service Ownership

| Service | Exclusive responsibilities |
| --- | --- |
| `ProductService` | Product/category mutation, publication, gallery, audit |
| `InventoryService` | Stock row locking, movements, projection updates, restock |
| `CartCalculator` | Pure integer price, discount, delivery, tax, and total calculation |
| `CustomerService` | Customer CRUD and conservative checkout matching |
| `OrderService` | Web placement, held-order persistence, status transitions, cancellation |
| `PaymentService` | Payment recording, aggregate status, references, till cash totals |
| `TillService` | Open/close invariants, expected cash, counted cash, variance |
| `PosCheckoutService` | POS validation and orchestration using shared order/payment/inventory services |

Services wrap writes in database transactions and record system activity after
the relevant models exist. Livewire components never mutate stock or order
status directly.

## 8. Transaction Invariants

1. `orders.total_minor` equals item totals plus delivery fee after discount.
2. A placed order has at least one item and a non-null order number.
3. Client-submitted prices and totals are ignored.
4. Product and stock rows are re-fetched during checkout.
5. Stock checks and decrements occur under row locks in the same transaction as
   order placement.
6. Failed stock validation leaves no placed order, item, payment, or movement.
7. Every stock change creates exactly one movement with matching before/after
   balances.
8. Cancelling a stock-committed web order creates compensating movements once.
9. Completed payment sum drives the aggregate order payment status.
10. A completed POS order belongs to an open till session.
11. A cashier cannot close a till with an in-flight checkout transaction.
12. Historical order/customer/product snapshots survive catalog or customer
    edits and soft deletion.

## 9. Required Test Matrix

- migration and factory creation for all models;
- money arithmetic and deterministic discount allocation;
- catalog validation, publication, gallery, filters, and permissions;
- stock movement/projection reconciliation;
- concurrent stock deduction and insufficient-stock rollback;
- web cart recalculation after product price or stock changes;
- guest checkout and optional signed-in checkout;
- order-number and public-token uniqueness/privacy;
- cancellation restores stock once;
- POS barcode/SKU search, hold/resume repricing, and checkout;
- split-payment aggregation and cash change;
- one-open-till invariant and close variance;
- activity records without sensitive payment metadata;
- storefront and dashboard light/dark responsive rendering;
- receipt and order-confirmation totals equal persisted snapshots.

## 10. Deferred Additive Tables

Future modules may add `product_variations`, `inventory_locations`,
`stock_reservations`, `coupons`, `reviews`, `wishlists`, `returns`, `refunds`,
`suppliers`, and `purchase_orders`. None are required to implement the approved
version-one flows and none should be scaffolded prematurely.
